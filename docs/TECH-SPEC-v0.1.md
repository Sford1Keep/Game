# TECH-SPEC v0.1 — [Рабочее название]

> Основа для нарезки атомарных задач под реализацию. Дизайнерский источник истины — GDD-lite v0.1. Здесь фиксируются решения, которые НЕ должен придумывать исполнитель кода: стек, протокол, схемы данных, структура репозитория.

## 1. Стек

- **Язык:** TypeScript везде (сервер, клиент, общий пакет типов) — единый язык снижает трение между слоями и упрощает работу LLM-исполнителя.
- **Сервер:** Node.js, авторитетная модель (сервер — источник истины по позициям, урону, кулдаунам, инвентарю, валюте).
- **Сетевой фреймворк инстансов: Colyseus.** Инстанс (зона/данж/рогалик-забег/гильд-рейд) реализуется как "комната" Colyseus — фреймворк даёт из коробки синхронизацию состояния (снапшоты/дельты клиентам), матчмейкинг в комнату, reconnect. Это закрывает сетевую "сантехнику", которую иначе пришлось бы писать вручную, и напрямую соответствует архитектуре "своя инстанса на игрока/пати".
- **Транспорт для остального:** обычный HTTP/REST для нечувствительных ко времени операций (аукцион, гильдии, профиль, лидерборды) — не через Colyseus, отдельный API-слой.
- **Клиент:** браузер, рендер через **Phaser** (2D, зрелый игровой фреймворк с физикой/анимациями/тайлмапами из коробки — выбран вместо PixiJS/Excalibur как более полный и проверенный на проектах такого масштаба). Игровая логика (правила, расчёты) — отдельный слой на чистом TS, не завязанный ни на Phaser, ни на Colyseus-клиент напрямую, чтобы его можно было переиспользовать при переходе на нативный клиент позже. Colyseus имеет клиенты не только для браузера — переход на нативный клиент меняет рендер-слой (Phaser → другой движок), а не сетевой протокол.
- **База данных: PostgreSQL** (подтверждено) — для персистентных данных (аккаунты, персонажи, инвентарь, гильдии, территории, лидерборды). Кэш/эфемерное состояние активных инстансов — в памяти процесса (управляется Colyseus), не в БД.
- **Пакетный менеджер / монорепо:** npm workspaces (или pnpm) для общих типов между клиентом и сервером.

## 2. Архитектура верхнего уровня

```
[ Client (браузер, Phaser) ]  <—Colyseus (комнаты, WebSocket)—>  [ Instance Server ]
        |                                                                |
        |  <—HTTP/REST (аккаунт, инвентарь вне боя,                      |
        |     аукцион, гильдии, лидерборды)—>                            |
        v                                                                v
                    [ API / Application Server ]  <——>  [ PostgreSQL ]
```

- **Instance Server** (на Colyseus) — держит игровой инстанс (зону/данж/рогалик-забег/гильд-рейд) для конкретного игрока или пати как "комнату". Авторитетно считает боёвку, применяет статусы, валидирует результаты испытаний. По завершении инстанса — фиксирует результат (лут, опыт, счёт) через API-сервер в БД.
- **API-сервер** — персистентные данные вне активного боя: аккаунты, персонажи, инвентарь (простой), гильдии, аукцион, лидерборды, квестовый прогресс.
- Инстансы **изолированы по игроку/пати** — соответствует решению GDD о том, что мир не является единой общей ареной. Инстанс поднимается по запросу входа в зону/данж/испытание и закрывается по выходу/завершению.

## 3. Структура репозитория (монорепо)

```
/repo-root
  /packages
    /shared          — общие типы, схемы данных, константы, формулы (используются и клиентом, и сервером)
    /server-api       — HTTP/REST: аккаунты, инвентарь, гильдии, аукцион, лидерборды, квестовый прогресс
    /server-instance  — Colyseus-приложение: боевая логика, зоны, испытания, гильд-рейды (комнаты)
    /client           — Phaser-клиент + чистый TS-слой игровой логики (game-core), отделённый от рендера
  /content            — данные контента в виде конфигов (JSON/TS-объекты): предметы, таланты, классы, квесты, территории, мутаторы. НЕ хардкодится в коде логики.
  /docs               — GDD, TECH-SPEC, roadmap, changelog
```

Правило: **логика игры (game-core) не импортирует ничего из Phaser/DOM.** Рендер-слой клиента читает состояние из game-core и рисует его. Это прямое следствие решения "браузер — временная платформа".

## 4. Сетевой протокол (инстансы, Colyseus)

- **Транспорт:** WebSocket, управляется через Colyseus-комнаты — не реализуется вручную поверх голого WS.
- **Тип сообщений:** сериализация состояния через встроенный механизм Colyseus (schema-based state sync); прикладные события (намерения игрока, ивенты урона/лута) — как сообщения комнаты (room messages).
- **Тик сервера:** фиксированный тик-рейт комнаты (например, 20-30 Гц) для авторитетного пересчёта состояния боя — настраивается на уровне Colyseus room.
- **Модель клиент-сервер:**
  - Клиент отправляет **намерения** (intent) как сообщения комнаты: "двигаться в направлении X", "использовать способность Y", "уклониться".
  - Клиент делает **локальное предсказание** для отзывчивости (движение, анимация).
  - Сервер (room-логика Colyseus) валидирует и пересчитывает авторитетно (попадания, урон, кулдауны, столкновения); изменения состояния рассылаются клиентам автоматически через встроенный state sync (дельты, не полные снапшоты каждый раз).
  - Клиент **реконсилирует** (корректирует) своё предсказание при расхождении с полученным состоянием.
- **Базовые типы сообщений комнаты (черновой список, дорабатывается в реализации):**
  - `client→server`: `intent.move`, `intent.ability`, `intent.dodge`, а также штатные Colyseus join/leave для входа/выхода из инстансы.
  - `server→client`: изменения состояния — через встроенный schema sync Colyseus; прикладные разовые события (`event.damage`, `event.status`, `event.loot`, `instance.result` при завершении испытания/забега) — как room messages поверх этого.

## 5. Модель данных (ключевые сущности, укрупнённо)

> Здесь только состав сущностей и связи, не финальная SQL-схема — её детализирует исполнитель по этим ориентирам.

- **Account** — логин, донат-валюта (постоянная), косметика (владение), список персонажей.
- **Character** — принадлежит Account и текущему сезону; класс, уровень, общее древо талантов (прогресс по узлам), классовая ветка (выбранная развилка, если уже выбрана), инвентарь (слоты → Item), сезонная валюта, состояние сюжетного прогресса (пройденные квесты кампании).
- **Item** — тип, тир редкости, аффиксы (включая фракционные), слот-совместимость, механические модификаторы навыков (если применимо).
- **TalentNode** — принадлежит общему древу или классовой ветке; связи с другими узлами (для мостов/предпосылок); классовые ключевые узлы помечены как "переломные" (взаимоисключающие в рамках ветки).
- **Quest** — тип (личный/групповой/кампания), условия выполнения, награды, связь с классовой развилкой (для квестов возвышения), гейт локации/механики (для NPC-разблокировок).
- **Guild** — название, участники (роль: лидер/офицер/участник), суммарный счёт по территориям.
- **Territory** — владелец (Guild, может быть null), текущий накопленный счёт за цикл (3 дня), список бонусов владения (валюта/статы).
- **RaidAttempt / ChallengeResult** — лог попытки (испытание с фиксированными условиями): тип (спидран/ивент-челлендж/гильд-рейд на территорию), сид/условия, результат (время или очки), кто участвовал — источник для лидербордов и вклада в гильдию.
- **Season** — идентификатор, даты начала/конца, список активных сезонных механик-модификаторов.
- **BuildShare** — сериализованный снимок билда персонажа (таланты + конфигурация слотов, без самих предметов) с публичным идентификатором для шаринга/веб-превью.

## 6. Контент как данные

Всё, что относится к балансу и контенту (предметы, таланты, квесты, территории, мутаторы рогалика), хранится в `/content` как структурированные конфиги, а не в коде логики. Код читает конфиги и применяет к ним универсальные правила расчёта (формулы урона, скейлинга и т.д., которые живут в `/packages/shared`). Это даёт:
- Возможность добавлять контент без изменения кода логики.
- Точку, куда позже подключается арт (конфиг предмета ссылается на `spriteId`, которого может пока не быть — рендерится плейсхолдер).

## 7. Стандарты кода

- TypeScript strict mode везде.
- Игровая логика организована по доменам как отдельные сервисы/модули: `combat`, `inventory`, `talents`, `quests`, `economy`, `guilds` — минимальное пересечение ответственности между модулями, чтобы задачи для исполнителя были атомарными и не требовали трогать несколько доменов одновременно.
- Публичные интерфейсы модулей описываются явно (входы/выходы), чтобы задачи можно было формулировать как "реализуй модуль X по интерфейсу Y" без необходимости видеть весь остальной код.

## 8. Версионирование и фиксация изменений в разработке

> Отдельно от разделителя обновлений для игроков (см. ROADMAP) — это внутренний процесс на время разработки, обязателен для исполнителя кода.

### 8.1 Ветки
- `main` — всегда рабочее состояние, соответствует последней принятой (мной проверенной) задаче.
- `phase/N-название` — ветка на фазу roadmap (например, `phase/1-combat-core`).
- `task/номер-краткое-описание` — ветка на одну атомарную задачу из бэклога, ответвляется от `phase/N-...`, мержится обратно после ревью. Одна ветка = одна задача, не смешивать несколько задач в одной ветке.

### 8.2 Коммиты
Формат: `[тип](модуль): краткое описание`
- Типы: `feat` (новая функциональность), `fix` (исправление), `refactor`, `docs`, `chore`.
- Модуль — из доменов TECH-SPEC (`combat`, `inventory`, `talents`, `quests`, `economy`, `guilds`, `client`, `shared`).
- Пример: `feat(combat): implement dodge cooldown validation on server`.
- Один коммит — одно логическое изменение. Не смешивать рефактор и новую фичу в одном коммите.

### 8.3 Версии сборки (внутренние, не для игроков)
- Формат `0.PHASE.TASK` на время разработки (например, `0.3.12` — фаза 3, 12-я принятая задача внутри неё). Не путать с будущим `X.Y` из ROADMAP, который начнётся с релиза (`1.0`).
- Тег версии ставится только на `main` после того, как я принял задачу/набор задач по ревью — не самим исполнителем произвольно.

### 8.4 CHANGELOG
- `/docs/CHANGELOG.md`, обновляется при каждом мерже в `main`.
- Формат записи: дата, версия, список изменений по типу (Added / Changed / Fixed), со ссылкой на номер задачи из бэклога.
- Ведётся, чтобы я мог быстро понимать, что изменилось между ревью, не перечитывая весь код заново.

### 8.5 Задачи и приёмка
- Каждая задача в бэклоге получает номер (например, `T-042`) — используется в ветках, коммитах, CHANGELOG для трассируемости от задачи до кода.
- Если задача добавляет новый модуль/директорию — обновление `/docs/PROJECT-MAP.md` (раздел 9.3) входит в критерий приёмки этой задачи.
- Задача считается принятой только после моего ревью, не после того, как исполнитель считает её законченной.

## 9. Масштабируемость и лёгкость изменений

> Прямое требование из GDD: игра должна легко масштабироваться и быть удобной для изменения. Ниже — как это обеспечивается архитектурно, не общими словами.

### 9.1 Масштабирование нагрузки (инфраструктура)
- **Instance Server безсостояние между инстансами:** один процесс может держать много независимых Colyseus-комнат (зон/данжей/забегов), комнаты друг друга не знают и не блокируют. Colyseus поддерживает горизонтальное масштабирование через встроенный механизм присоединения к процессам (при необходимости — с координацией через Redis) — поднимать больше процессов/контейнеров при росте нагрузки можно без переписывания игровой логики.
- **API-сервер безсостоятелен (stateless) между запросами** — тоже горизонтально масштабируется за балансировщиком нагрузки, состояние живёт в БД, не в памяти процесса.
- **БД — единая точка правды**, но структура схем (раздел 5) уже разложена по доменам (инвентарь/гильдии/территории отдельно) — при необходимости в будущем можно вынести отдельные домены на отдельные БД/шарды без пересборки всей модели.
- Раз инстансы изолированы по игроку/пати (решение GDD), нагрузка линейно растёт с числом активных инстансов, а не с числом игроков в одной общей симуляции — это принципиально дешевле в масштабировании, чем честный shared-world.

### 9.2 Лёгкость изменения игры (контент и логика)
- **Контент как данные (раздел 6):** новый предмет/квест/территория/мутатор добавляется конфигом, без изменения кода. Баланс (числа урона, стоимости, шансы) — тоже вынесен в конфиги/константы `shared`, не зашит в логику по месту использования.
- **Разделение по доменам (раздел 7):** изменение экономики не требует трогать боёвку, изменение талантов не требует трогать гильдии. Задача на одну фичу — это правки в одном-двух модулях, не по всему кодовой базе.
- **Явные интерфейсы между модулями:** модуль боёвки не знает внутреннего устройства модуля инвентаря, только его публичный интерфейс (какие статы/эффекты он предоставляет). Замена реализации одного модуля не требует переписывать остальные.
- **game-core отделён от рендера (раздел 3):** смена платформы (браузер → нативный клиент) или смена рендер-движка не требует переписывать правила игры.
- Практическое следствие для темпа разработки: новую единицу контента (предмет, квест, зону) можно добавить силами одного атомарного задания исполнителя кода без риска задеть остальную систему — это и есть "лёгкость изменения" на уровне процесса, не только архитектуры.

### 9.3 Файл-проводник по проекту
- `/docs/PROJECT-MAP.md` — единый навигационный документ: где что лежит и за что отвечает.
- Обязательное содержимое: список директорий/модулей с однострочным описанием назначения каждого (что в нём, за какой домен отвечает, с чем связан); для `/content` — какие типы конфигов там и в каком формате; ссылки на связанные разделы TECH-SPEC для каждого модуля.
- **Обновляется при каждой задаче, которая добавляет новый модуль/директорию** — это часть критерия приёмки задачи (раздел 8.5), не отдельная работа "когда-нибудь потом".
- Назначение: и мне, и тебе, и исполнителю кода — не тратить время на "где это искать", открыть один файл и понять структуру проекта целиком без чтения всего кода.

## 10. Вне скоупа TECH-SPEC v0.1

- Точный тик-рейт, формат бинарного протокола (если понадобится оптимизация) — решается при реализации сетевого слоя.
- Античит для аукциона/фарма.
- Конкретные числа баланса экономики/боёвки.
- Нативный клиент (PC/mobile) — архитектура закладывается совместимой, реализация — позже.
