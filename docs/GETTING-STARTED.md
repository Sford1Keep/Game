# GETTING-STARTED — с чего начать

> Этот файл — точка входа. Прочитать первым, до GDD и TECH-SPEC.

## Что это за документы

- **`GDD-lite-v0.1.md`** — что за игра, какие в ней системы и почему они так устроены. Источник истины по геймдизайну.
- **`TECH-SPEC-v0.1.md`** — как это технически реализовано: стек, архитектура, протокол, модель данных, правила версионирования, структура проекта, требования к масштабируемости.
- **`ROADMAP-v0.1.md`** — в каком порядке всё это строится, разбито на фазы с критериями готовности каждой.

Порядок чтения для исполнителя кода: **GETTING-STARTED → TECH-SPEC → ROADMAP → GDD (по мере необходимости для конкретной задачи)**. TECH-SPEC — рабочий документ, GDD нужен точечно, когда задача требует понимания игрового смысла, а не только технической реализации.

## Роли

- **Лид (дизайн/архитектура/ревью):** ведёт GDD и TECH-SPEC, нарезает задачи, ревьюит и принимает код, имеет прямой доступ на чтение к репозиторию.
- **Исполнитель кода (LLM):** реализует задачи по спецификации, не принимает самостоятельных архитектурных решений вне того, что явно оставлено "на усмотрение исполнителя" в задаче.
- **Автор нарративных текстов (отдельный LLM-инструмент):** пишет диалоги/квестовые тексты по структуре квестов, заданной в GDD/бэклоге — не участвует в коде.

## Репозиторий

- **GitHub:** `https://github.com/Sford1Keep/Game` (публичный).
- Лид имеет прямой доступ на чтение (клонирование/просмотр файлов и истории коммитов) — не требуется вручную передавать файлы для ревью, достаточно ссылки на коммит/PR или просьбы посмотреть текущее состояние.
- **Пуш в репозиторий** делают только Max или исполнитель кода — у лида нет прав на запись.

## Стек (подтверждён)

- **Язык:** TypeScript везде.
- **Сервер (инстансы):** Node.js + **Colyseus** — сетевой фреймворк для комнат/инстансов в реальном времени, закрывает синхронизацию состояния, матчмейкинг и reconnect из коробки.
- **Сервер (остальное):** HTTP/REST для аккаунтов, инвентаря вне боя, аукциона, гильдий, лидербордов.
- **Клиент:** браузер, рендер через **Phaser**.
- **База данных:** **PostgreSQL**.
- Подробности архитектуры и протокола — в TECH-SPEC, разделы 1-4.

## Порядок работ на старте

1. **Инициализация репозитория.** Создать монорепо по структуре из TECH-SPEC (раздел 3): `/packages/shared`, `/packages/server-api`, `/packages/server-instance` (Colyseus), `/packages/client` (Phaser), `/content`, `/docs`. Перенести `GDD-lite-v0.1.md`, `TECH-SPEC-v0.1.md`, `ROADMAP-v0.1.md` в `/docs`.
2. **Завести `/docs/PROJECT-MAP.md`** (см. TECH-SPEC, раздел 10.3) — даже пустой каркас с разделами под каждую будущую директорию, дальше пополняется по ходу задач.
3. **Завести `/docs/CHANGELOG.md`** (см. TECH-SPEC, раздел 8.4) — пустой файл с заголовком, готовый к первым записям.
4. **Настроить ветки.** `main` как базовая ветка, дальше `phase/0-foundation` под первую фазу.
5. **Взять Фазу 0 из ROADMAP** и нарезать её на атомарные задачи (`T-001`, `T-002`, ...) — это первая работа лида после инициализации репозитория.
6. **Каждая задача передаётся исполнителю кода** в формате: номер задачи, ссылка на релевантный раздел TECH-SPEC/GDD, вход/выход, критерий приёмки (что должно быть проверяемо истинным, чтобы задача считалась готовой).
7. **Ревью и приём** — лид проверяет код/дифф по критерию приёмки задачи (читает репозиторий напрямую или получает ссылку на изменения), при необходимости правит саму задачу/спеку (если она оказалась неточной), затем задача мержится в `phase/N-...`.
8. По закрытии всех задач фазы — мерж `phase/N-...` в `main`, отметка в CHANGELOG, переход к следующей фазе ROADMAP.

## Что не нужно решать сейчас

- Точные числа баланса, арт, названия территорий/предметов — эти вещи наполняются по ходу фаз, не блокируют старт Фазы 0.
- Название игры — можно оставить плейсхолдер до момента, когда это понадобится в UI/на титульном экране.
