# BACKLOG — Фаза 1 (Боевое ядро)

> Критерий готовности фазы (см. ROADMAP): можно убить моба активной боёвкой, урон и кулдауны считает сервер, а не клиент.
> Предпосылка: Фаза 0 смержена в `main` (T-001–T-009 включая T-004 — см. примечание в конце). Ветка фазы: `phase/1-combat-core`, ответвляется от `main` после мержа Фазы 0. Задачи — `task/T-0XX-...` от неё. Формат коммитов/версий — TECH-SPEC, раздел 8.

## T-010 — Диагностическое логирование

- **Вход:** Фаза 0 в `main`.
- **Выход:** в `packages/shared` — фабрика `createLogger(context)` на `pino` (TECH-SPEC 10.1). Интеграция в уже существующие `server-api` и `server-instance`: замена любых `console.log`/самодельных выводов на логгер, middleware `requestId` в `server-api` (HTTP), контекст `instanceId`/`sessionId` в `server-instance` (Colyseus room). Уровень читается из `LOG_LEVEL`, `pino-pretty` в dev.
- **Критерий приёмки:** намеренно брошенная ошибка (тестовый сценарий) даёт в логе структурированную запись с стеком и корреляционным id; обычный HTTP-запрос к `server-api` логируется с `requestId`; в коде нет `catch` без вызова логгера (проверяется по диффу ревью).
- **Связанные разделы:** TECH-SPEC 10.1.

## T-011 — Игровые события (`GameEvent`)

- **Вход:** T-010 закрыт (использует тот же `shared`, логически рядом).
- **Выход:** схема `GameEvent` в `packages/shared` (`type`, `actorId`, `payload`, `instanceId`, `timestamp`), таблица/миграция в `server-api` (append-only, по образцу миграции `accounts` из T-003), функция записи события (вызывается из `server-api`; `server-instance` не пишет в БД напрямую — раздел 2 TECH-SPEC, событие уходит через API-слой). Типы событий на старте: `mob.killed`, `item.looted` (даже если сам лут ещё не реализован — зарезервировать тип).
- **Критерий приёмки:** тест — запись события через функцию-writer появляется в таблице БД с корректными полями; повторная запись не перезаписывает предыдущую (append-only).
- **Связанные разделы:** TECH-SPEC 5, 10.2.

## T-012 — `shared`: боевые типы

- **Вход:** T-011 закрыт.
- **Выход:** в `packages/shared` — типы урона и статус-эффектов: `DamageInstance` (источник/цель/величина/тип), `StatusEffectId` (начать с `vulnerable`), `AbilityId`, кулдауны как `{ abilityId, readyAtMs }`. Расширение схемы контент-конфигов (`content.ts`, T-009) под `AbilityConfig` (урон, кулдаун, дальность/радиус) и `MobConfig` (уже есть — добавить HP, урон атаки, радиус агро).
- **Критерий приёмки:** типы и расширенный парсер конфигов компилируются и импортируются из `server-instance`/`client` без ошибок; юнит-тест на парсинг `AbilityConfig` из JSON (аналогично `content.test.ts` из T-009).
- **Связанные разделы:** TECH-SPEC 5, 6.

## T-013 — `content`: конфиги способностей и обновление моба

- **Вход:** T-012 закрыт.
- **Выход:** в `/content` — 1-2 конфига активных способностей (атака, уклонение — уклонение может быть механикой без конфига, если это не «способность» в игровых терминах, отдельно реши на своё усмотрение и зафиксируй в PROJECT-MAP почему) и обновлённый конфиг моба (`rust-scout.json` из T-009 — добавить HP/урон/агро-радиус).
- **Критерий приёмки:** конфиги валидны по схеме T-012, `PROJECT-MAP.md` обновлён с описанием новых полей.
- **Связанные разделы:** TECH-SPEC 6, 9.2.

## T-014 — `server-instance`: обработка `intent.ability` и `intent.dodge`

- **Вход:** T-012, T-013 закрыты.
- **Выход:** в `BaseInstanceRoom` (или наследнике под боёвку) — обработчики сообщений `intent.ability`, `intent.dodge`, аналогично существующему `intent.move` (T-006): валидация кулдауна на сервере (если способность не готова — сообщение отклоняется без побочных эффектов), обновление `readyAtMs` в состоянии игрока.
- **Критерий приёмки:** интеграционный тест (по образцу `intentMove.test.ts`) — способность до истечения кулдауна отклоняется, после истечения проходит; некорректный `abilityId` отклоняется без падения комнаты.
- **Связанные разделы:** TECH-SPEC 4.

## T-015 — `server-instance`: простой моб с агро и атакой

- **Вход:** T-013 закрыт (не зависит от T-014, можно параллельно).
- **Выход:** моб как сущность в состоянии комнаты (по образцу `PlayerState` в `state.ts` — добавить `MobState`: позиция, HP, статус агро/цель). Простейший AI на тике комнаты: моб в радиусе агро выбирает ближайшего игрока целью и атакует по таймеру (переиспользует константы урона/кулдауна из конфига T-013).
- **Критерий приёмки:** интеграционный тест — моб появляется в state при старте комнаты; при входе игрока в радиус агро моб выставляет цель и через N мс наносит урон (проверяется по изменению HP игрока в state).
- **Связанные разделы:** TECH-SPEC 4, 5.

## T-016 — `server-instance`: расчёт урона, статус «уязвимость», запись событий

- **Вход:** T-014, T-015, T-011 закрыты.
- **Выход:** единая функция применения `DamageInstance` к цели (игроку или мобу) — уменьшает HP, публикует `event.damage`. Статус `vulnerable` на мобе — модификатор увеличивает входящий урон на фиксированный процент на время действия; накладывается способностью из T-014 (одна из двух — например, атака дальника помечает моба уязвимым). Смерть моба (HP ≤ 0) убирает его из state, рассылает `event.loot`-заглушку клиенту и пишет `GameEvent` типа `mob.killed` (T-011) через API-слой.
- **Критерий приёмки:** тест — урон по мобу без статуса и с статусом `vulnerable` даёт разный итоговый HP при одинаковом входном уроне; смерть моба убирает его из state; в таблице `GameEvent` появляется запись `mob.killed` с корректным `actorId`.
- **Связанные разделы:** TECH-SPEC 4, 10.2, GDD раздел 4 (статусы как кооп-синергия).

## T-017 — `client`: атака и уклонение — ввод и отправка

- **Вход:** T-012 закрыт (не зависит от остальных серверных задач, можно параллельно с T-014–T-016).
- **Выход:** в `client/src/game-core` — обработка ввода атаки/уклонения (клавиши), учёт локального кулдауна для мгновенного фидбека (аналогично `MovementController` из T-008 — локальное предсказание, не ждём сервер для визуальной реакции), отправка `intent.ability`/`intent.dodge` через `net/instanceSession.ts`.
- **Критерий приёмки:** нажатие клавиши атаки до истечения локального кулдауна визуально блокируется; после — интент уходит на сервер (проверяется тестом на стороне `game-core`, без браузера, по аналогии с `movement.test.ts`).
- **Связанные разделы:** TECH-SPEC 4, 9.2.

## T-018 — `client`: рендер HP, урона и статусов (плейсхолдер)

- **Вход:** T-016, T-017 закрыты.
- **Выход:** в `client/src/render/instanceScene.ts` — полоска HP над игроком/мобом (примитив, без арта), визуальный индикатор статуса `vulnerable` на мобе (например, смена цвета плейсхолдер-квадрата), всплывающее число урона при `event.damage` (плейсхолдер-текст).
- **Критерий приёмки:** ручная проверка — при бое HP визуально меняется синхронно с `state`, `vulnerable`-статус отличим на глаз, смерть моба убирает его со сцены.
- **Связанные разделы:** TECH-SPEC 9.2.

## T-019 — Сквозной сценарный тест «убить моба»

- **Вход:** T-014–T-016 закрыты.
- **Выход:** интеграционный тест в `server-instance` (по аналогии с `instanceRoom.test.ts`) — полный сценарий: игрок заходит в комнату → моб агрится → игрок атакует несколько раз (с выдержкой кулдауна) → HP моба падает до 0 → моб удаляется из state → в таблице `GameEvent` появляется `mob.killed`.
- **Критерий приёмки:** тест проходит стабильно (без флейков по таймингу — если тесты зависят от `Date.now()`, использовать инжектируемые часы как в `MovementController`, T-008).
- **Связанные разделы:** TECH-SPEC 7, 8.5.

---

**Примечание про T-004.** Задача создания персонажа (из бэклога Фазы 0) на момент нарезки этого бэклога не реализована. Она не блокирует ни одну задачу Фазы 1 напрямую (боёвка тестируется на уровне комнаты/state, без реального аккаунта), но без неё нет актуальной цепочки «аккаунт → персонаж → инстанс» целиком. Рекомендация: закрыть T-004 параллельно с началом Фазы 1, не позже T-014, иначе к концу фазы придётся возвращаться и стыковать боёвку с несуществующей системой персонажей.

По закрытии всех задач — критерий готовности Фазы 1 проверяется вручную: клиент убивает моба активной боёвкой, сервер отклоняет способности до истечения кулдауна, статус `vulnerable` видимо влияет на урон, событие смерти моба видно в таблице `GameEvent`. После этого — мерж `phase/1-combat-core` в `main`, запись в CHANGELOG, переход к Фазе 2.
